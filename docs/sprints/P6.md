# P6: Community updates and admin review
Status: Implemented (owner check pending)
Goal: Classmates keep listings fresh; the admin approves every change before it goes public.
Scope: "Still open?" checks, `/submit`, `/admin` review queue, admin role editor, `/admin/import` CSV; excludes email notifications.
Depends on: P1 to P5

## Decisions
- Carry-over fixed first: the public API can't read any column that points at a person (`created_by`, `last_checked_by`, `added_by`, `updated_by`). The listing view names its columns; base tables use column-level grants.
- Still open: one check per person per role per day. "Open" refreshes "checked". When `app_config.closed_report_threshold` (2) different people report closed or dead within the re-check window, a "post closed" item goes to the queue. Posts never close by themselves.
- Submissions: new role, or an update (closed, pay, hours, MOA, bounced email, correction) with a link or note. Summaries only, no names or personal numbers.
- Review runs in one database function (`review_submission`), so applying and marking reviewed can't half-happen. New roles land as drafts with a "needs clarification" partnership until checked. Pay, hours, MOA and corrections are kept as evidence; the admin edits the role fields with the role editor.
- CSV import: roles go through the same review path (drafts with a trail, max 200 rows); an HTE list imports as a new version and can become the current list in the same transaction.
- Admins see a queue badge in the top bar; everyone signed in sees "Share an update".
